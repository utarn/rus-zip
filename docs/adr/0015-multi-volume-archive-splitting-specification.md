# 0015: Stream-Level Multi-Volume Archive Splitting and Naming Specification

We decided to implement multi-volume archive splitting across `rus-zip` using continuous stream-level slicing with the `<base>.part<N>.<ext>` naming convention, supporting split size presets (100MB, 250MB, 1GB, 2GB, 4GB, 10GB) and custom thresholds, with seamless multi-volume decompression and fail-fast missing volume validation.

## Context
Users frequently need to split large archives (or archives containing single huge files exceeding partition limits) into fixed-size storage volumes (such as 100MB, 250MB, 1GB, 2GB, 4GB for FAT32 filesystems, or 10GB for cloud storage limits).
- Split archives must seamlessly span arbitrary content streams, whether compressing thousands of small files or single multi-gigabyte files.
- The naming convention must be unambiguous, clean, and broadly compatible.
- The decompression engine must detect multi-volume archives automatically when opening `part1` (or any part in the series) and stream through subsequent parts in sequence.

## Decision

### 1. Volume Naming & Discovery Standard
- **Creation Format**: `<base>.part<N>.<ext>` (e.g., `backup.part1.zrus`, `backup.part2.zrus`, ... or `data.part1.zip`, `data.part2.zip`).
- **Reader Flexibility**: The volume resolver accepts both unpadded (`.part1`, `.part2`) and zero-padded variants (`.part01`, `.part001`) to support archives generated by different utilities.
- When any part of an archive is passed to `extract`, `list`, or `test`, the engine locates the first volume (`.part1` / `.part01` / `.part001`) in the containing directory and verifies sequential continuity.

### 2. Multi-Volume Stream Architecture
In [`src/RusZip.Core/Engines/MultiVolumeWriteStream.cs`](../../src/RusZip.Core/Engines/MultiVolumeWriteStream.cs) and [`src/RusZip.Core/Engines/MultiVolumeReadStream.cs`](../../src/RusZip.Core/Engines/MultiVolumeReadStream.cs):

```csharp
public sealed class MultiVolumeWriteStream : Stream
{
    private readonly string _basePath;
    private readonly string _extension;
    private readonly long _maxVolumeBytes;
    private int _currentPartIndex = 1;
    private FileStream _currentStream;
    private long _currentPartBytesWritten;

    public MultiVolumeWriteStream(string destinationPath, long maxVolumeBytes)
    {
        _maxVolumeBytes = maxVolumeBytes;
        (_basePath, _extension) = SplitBaseAndExtension(destinationPath);
        _currentStream = CreateVolumeStream(_currentPartIndex);
    }

    public override void Write(byte[] buffer, int offset, int count)
    {
        while (count > 0)
        {
            var remainingInVolume = _maxVolumeBytes - _currentPartBytesWritten;
            if (remainingInVolume <= 0)
            {
                _currentStream.Dispose();
                _currentPartIndex++;
                _currentStream = CreateVolumeStream(_currentPartIndex);
                _currentPartBytesWritten = 0;
                remainingInVolume = _maxVolumeBytes;
            }

            var toWrite = (int)Math.Min(count, remainingInVolume);
            _currentStream.Write(buffer, offset, toWrite);
            _currentPartBytesWritten += toWrite;
            offset += toWrite;
            count -= toWrite;
        }
    }
    // ...
}

public sealed class MultiVolumeReadStream : Stream
{
    private readonly IReadOnlyList<string> _volumeFilePaths;
    private int _currentIndex = 0;
    private FileStream _currentStream;

    public MultiVolumeReadStream(IReadOnlyList<string> volumeFilePaths)
    {
        if (volumeFilePaths.Count == 0) throw new ArgumentException("At least one volume required.");
        _volumeFilePaths = volumeFilePaths;
        _currentStream = File.OpenRead(_volumeFilePaths[0]);
    }

    public override int Read(byte[] buffer, int offset, int count)
    {
        while (count > 0)
        {
            var bytesRead = _currentStream.Read(buffer, offset, count);
            if (bytesRead > 0) return bytesRead;

            // Move to next volume
            _currentStream.Dispose();
            _currentIndex++;
            if (_currentIndex >= _volumeFilePaths.Count)
            {
                return 0; // EOF reached across all volumes
            }

            _currentStream = File.OpenRead(_volumeFilePaths[_currentIndex]);
        }
        return 0;
    }
    // ...
}
```

### 3. Presets & Size Parsing
- Add standard presets to [`src/RusZip.Core/Models/DataSizeParser.cs`](../../src/RusZip.Core/Models/DataSizeParser.cs):
  - `100MB` (104,857,600 bytes)
  - `250MB` (262,144,000 bytes)
  - `1GB` (1,073,741,824 bytes)
  - `2GB` (2,147,483,648 bytes)
  - `4GB` (4,294,967,296 bytes)
  - `10GB` (10,737,418,240 bytes)
  - Custom size strings (e.g. `500MB`, `1.5GB`) parsed via `DataSizeParser.TryParse(input, out long bytes)`. Minimum allowed volume size is 64 KB (`65,536` bytes).

### 4. Missing Volume Fail-Fast Policy
- When beginning multi-volume extraction or testing:
  - If a part is missing in sequence (e.g. `part1` and `part3` exist, but `part2` is missing), the engine throws `MissingVolumeException($"Volume part2 is missing: expected '{expectedPartPath}'.")`.
  - [`SafeArchiveExtractor`](../../src/RusZip.Core/Engines/SafeArchiveExtractor.cs) automatically catches the failure and performs atomic cleanup of any partial files extracted before the missing volume was reached.

### 5. Immutability Constraints
- Appending (`AppendAsync`) or entry deletion (`DeleteEntriesAsync`) on multi-volume split archives is strictly disallowed and throws `NotSupportedException("Modifying multi-volume split archives is not supported.")`.

### 6. CLI & GUI Integration
- **CLI**:
  - `rus-zip compress <sources...> -o <dest> -s <SIZE>` (e.g. `rus-zip c ./large_folder -o backup.zrus -s 1GB`).
  - Progress tracker prints active volume progress: `Compressing [backup.part2.zrus] (Volume 2) [=====>    ] 45%`.
- **Desktop**:
  - Compression Settings View includes a Split Volume toggle and Preset Dropdown (`100 MB`, `250 MB`, `1 GB`, `2 GB`, `4 GB`, `10 GB`, `Custom...`).
  - Segmented Status Bar displays `📦 Multi-Volume (N parts)` when viewing a split archive.

## Consequences
- Clean, predictable multi-volume compression that seamlessly handles large directories and multi-gigabyte single files.
- Robust, fail-fast decompression with atomic safety guardrails.
- Standardized, consistent naming across all supported archive formats.
